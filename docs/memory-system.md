# 长期记忆系统

agent100 在一次聊天正常结束时，从本次运行产生的用户与助手正文中提取长期记忆。工具调用、工具结果等序列化事件不会进入提取请求，临时记忆和无法在原对话中找到证据的候选记忆会被过滤。

## 保存流程

1. 模型从本次对话生成结构化候选记忆。
2. GLM Embedding-3 一次性将全部候选正文转换为 512 维向量。
3. 每条候选先按 `key` 全局查询旧记忆，再以余弦相似度全局查询相关记忆。
4. 决策模型根据候选与旧记忆选择 `add`、`confirm`、`replace` 或 `ignore`。
5. 服务层执行决策：新增记忆、增加确认次数、写入替代记忆并删除旧记忆，或者忽略候选。

每条正式记忆的 Qdrant point 包含正文向量和 payload。payload 保存 ID、正文、类型、稳定 key、scope、重要性、置信度、时效类型、证据、状态、时间及确认次数。向量只由 `content` 生成。

候选记忆和 replacement 必须由模型明确填写 `status`：`active`（有效）、`superseded`（修正、撤销或废弃）、`expired`（过期）。ADD 原样保存候选状态，REPLACE 原样保存替代记忆状态并删除旧记录；CONFIRM 不改变状态，状态变化必须使用 REPLACE。检索默认仅返回 active 记忆。撤销/过期候选即使属于 temporary 也参与处理，避免旧记忆残留有效状态。

已删除 `valid_from`、`valid_until` 字段；读取旧库时兼容忽略这两个历史字段，不对现有数据库执行批量修改。

当前旧记忆语义查询使用 `0.5` 相似度阈值，最多返回 10 条；相同 `key` 的记忆通过精确查询参与决策。`scope` 作为记忆元数据保留，但不参与查重召回过滤。

向量查询使用服务端 HNSW 近似检索（`m=16`、`ef_construct=128`、查询 `hnsw_ef=128`），降低全扫描和索引构建阈值。索引由服务端异步构建，不设置 `indexed_only`，避免遗漏尚未索引的新记忆；小片段或正在建索引的数据仍可能扫描。

`find_by_key` 使用 Qdrant 原生 KEYWORD payload 索引，精确匹配完整的 `key` 和 `status`，不按 scope 过滤、不进行 BM25 模糊检索。集合初始化时建立缺失的 key/status 索引，写入和删除时由服务端自动维护，不需要客户端全量加载 key 或维护额外缓存。

## 查询流程

`search_memory` 是模型按需调用的只读工具。工具可接收最多 5 条查询，并按以下方式合并结果：

- 已知稳定 key 时，先按 `key` 全局精确查询最多 10 条。
- 将全部查询文本一次性向量化，每条查询全局返回最多 5 条相似度不低于 `0.6` 的记忆。
- 按记忆 ID 去重；同一记忆被多个查询命中时保留最高相似度。

## 配置与存储

向量化固定使用 GLM Embedding-3，因此必须在 `data/.env` 中配置 `ZAI_API_KEY`。聊天模型可以选择 GLM 或 DeepSeek，候选提取和记忆决策使用当前聊天模型。

记忆库使用 Qdrant 服务端模式，默认连接 `http://127.0.0.1:6333`，集合为 `memories`（512 维 Cosine）。首次配置会在数据目录 `.env` 中写入固定的 `QDRANT_URL`；旧配置未包含该项时使用相同默认地址。运行前必须启动本机 Qdrant 服务。

旧内嵌库不会自动迁移。停止 agent100 后执行 `python scripts/migrate_memory.py`，将默认旧库 `data/memory/qdrant` 中的 ID、payload 和向量原样迁至服务端，并验证迁移结果。自定义旧库目录时传入 `--source`。迁移不会重新向量化或删除旧库，也不会修改法规 Batch 任务。

## 当前限制

保存流程按候选顺序执行，尚未提供事务回滚：如果中途请求失败，之前已经执行的记忆决策会保留。DeepSeek JSON Output 偶尔可能返回空正文，候选提取会最多尝试三次，并在重试请求中补充明确的 JSON 输出要求。
